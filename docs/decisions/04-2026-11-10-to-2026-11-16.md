# Decisions, 2026-11-10 to 2026-11-16

## 2026-11-10: Layouts are saved and loaded as BandageNG does; no session files

- **Decision**: the session file (`.grape.json.gz`: a view and float32
  positions) is removed. Export writes BandageNG's layout files
  (layout/io.cpp in asl/BandageNG): `.layout`, a JSON object from node name
  and strand (`name+`, and `name-` backwards in double mode) to the node's
  line points, and `.tsv`, one line per node with the middle point of its
  line at `%g` precision. Opening a `.layout` file applies it to the open
  graph, as BandageNG's Load layout does: names the graph lacks are refused
  with its messages, and segments the file leaves out are hidden (a filter
  that Clear removes). Each line is resampled along its length onto the
  segment's chain and scaled by the median ratio of chain length to line
  length, since Bandage's units are not GRAPE's; a file whose lines all have
  their chain's point count, as GRAPE writes them, is used exactly, so an
  exported layout draws again bit for bit on either renderer. The original
  Bandage (rrwick) has no layout files.
- **Reason**: the owner asked that saving a drawing match Bandage. BandageNG's
  format is the one Bandage users have, needs no format of GRAPE's own, and
  the fixed-layout path built for sessions already draws given positions.
- **Alternatives**: keeping session files beside layout files; placing the
  segments a layout leaves out around the pinned ones instead of hiding
  them.

## 2026-11-14: Graph look (release stage 11.1)

- **Decision**: nine fixes from the ux-review of labels, ribbons and links, all
  approved by the owner.
  - Dimmed ribbons fade into the background colour (`DIMMED` 0.35, was 0.25
    alpha) instead of going translucent, so the overlap at piece joints shows
    no darker dots. The hover outline is opaque (selection colour mixed with
    the background), for the same reason. The SVG export fades the same way.
  - The selection outline is two rings, an outer one in the selection colour
    and an inner one in `selectionInner` (white in light, dark navy in dark),
    each its own pass so neither overdraws the other at joints; the minimum
    width is 3 pixels, 1.5 a ring. SVG draws the same two rings.
  - Floating panels are opaque (`--panel` had 0.9 alpha, which let ribbons and
    labels show through the text).
  - Links keep 0.4 of full strength at ribbons 1 pixel wide and fade out by
    0.2 pixels, draw at least 1.5 pixels wide, and their Bézier handle is
    capped at half the gap between the ends (the loop case for ends that meet
    is unchanged), which removes the squiggles between close segments.
  - Labels are 14 px (was 12) with a 1.5 px halo (was 1). They do not grow with
    the ribbon: the GPU placement measures every label at one font size. With
    ribbons under "from ribbons" pixels, a segment is still labelled when its
    chain is on screen at least as long as its label is wide (`fit` in the
    placement of both backends); under 0.1 px no placement runs, so a huge
    graph at fit costs nothing. "No label fits at this zoom" shows when none
    does.
  - A segment on several highlighted paths is striped across its width, up to
    four stripes, first path on the side of lower y; the segment table gains
    `path2` to `path4` (12 bytes a segment). SVG draws the stripes as offset
    strokes.
  - Search hit bands get a 1 px edge in the link colour. The SVG edge is a
    wider stroke under the band, so it has no edge at the flat ends.
  - Ribbon bends are smoothed on screen: each piece is drawn as 4 capsules
    along a uniform Catmull-Rom curve through the chain's points once ribbons
    are 2 pixels wide, so ends and links stay put. Bands, box select and
    queries still use the straight pieces.
- **Reason**: audit screenshots of the four examples and four test graphs on
  both backends, both themes (docs/graph-look/before and after). Smoothing is
  screen only because PNG and SVG exports must match Bandage's straight
  pieces; `pixelScale` set (exports) draws one capsule per piece as before.
  Piece counts stay Bandage's because BandageNG layout files hold the points.
- **Alternatives**: more pieces per segment (breaks layout files); smoothing in
  exports too (exports stop matching Bandage); scaling label size with ribbon
  width (needs per-label sizes in the placement pass); a floor under link
  fade at any width (draws every link of a 1M graph at fit).
- **Measured**: GPU time per frame while zooming on the mitochondrion and lpa
  examples, WebGPU, was 0.5 to 0.6 ms with and without smoothing. The 200k
  and 1M graphs were not measured.

## 2026-11-15: Shell redesign (release stage 11.2)

- **Decision**: the owner approved the audit's four fix groups, the **Bench**
  direction (a cool grey-blue instrument panel with a cobalt accent) and five
  sidebar tabs.
  - **Tokens** (`ui/styles/tokens.css`): canvas `#fbfcfd` / `#171c23`, chrome and
    panel, ink, muted, accent `#2457d6` / `#7da2ff`, warning `#9a4f00` /
    `#e8b45a`, a hairline `--border` for panels and a `--control-border` of 3:1 or
    better for every control. `palettes` in engine/style/palette.ts clears the canvas
    to the same background. `tests/unit/tokens.test.ts` checks every text pair
    at 4.5:1 and every control border at 3:1 on panel, chrome and canvas, in both
    themes (WCAG 1.4.3 and 1.4.11); no axe dependency was added. System UI
    fonts, JetBrains Mono for sequences.
  - **Tabs**: Overview, Display, Find, Paths, Layout. Filters live in Find ("Limit
    the view"), seed, quality, pause and pins in Layout, and the thresholds
    (labels shown, link and dot widths) under a collapsed "Detail" group in Display
    with plain wording. Find switches between "By name" and "By sequence"; the
    mode is in the store so the `/` shortcut returns to names.
  - **Top bar**: one split Open button (the button opens the file picker, the arrow
    opens Open from URL and Examples), Export, Share, then theme and help
    icons (SVG, 32 px targets). The empty state has one primary "Open a file".
  - **Progress**: a strip under the top bar with a native `<progress>` and a chip
    per task. Loading and sequence indexing can be cancelled; the layout can be
    paused and resumed. There is no Stop for the layout because the engine has no
    such action; adding one would leave a half-refined picture. Level and energy
    moved to a tooltip.
  - **Info panel**: Zoom to and Copy sequence up front, Whole component, Invert and
    Download FASTA under "More actions"; neighbours are chips; toasts sit
    bottom-centre (top on narrow windows). A load with warnings toasts
    "N lines were skipped or repaired" with a Review button.
  - **Narrow windows**: below 900 px the sidebar and the info panel are bottom
    sheets (46% of the height, one at a time: a selection's details replace the
    sidebar until cleared) and the camera fit uses a bottom inset; below 720 px the
    top bar drops its brand and menus open across the window. Every action stays on
    screen down to 390 px, so the planned "⋯" menu was not needed.
  - **Onboarding**: a first-run card at the top of the Overview, dismissed once
    (`welcomed` in the saved settings), and a help overlay with a "Coming from
    Bandage" table. Its Bandage terms are from ui/mainwindow.ui in rrwick/Bandage
    (Load graph, Draw graph, Graph scope, Colour by, Node labels, Find nodes,
    BLAST, Save image).
- **Reason**: the audit of 114 screenshots (docs/shell/before and after): at 390 px
  the top bar overflowed and the sidebar hid the graph; the Display tab held six
  groups of unrelated controls; control borders were 1.4:1; the empty state and the
  Examples menu repeated each other.
- **Alternatives**: the Stain and Console directions; four tabs with disclosures; a
  menu-only Open button; a Stop for the layout; an axe dependency for contrast.

## 2026-11-15: Memory (release stage 11.3)

- **Decision**: the owner kept the spec's tab targets (300 MB up to 5,000
  segments, 1 GB up to 200,000, 2 GB above) and asked for the GPU part of the
  1M graph to fit its budget. A settled GPU layout now gives back the forces and
  the spatial grid, which only iterating uses (`GpuLevel.release`), and builds
  them again when a refinement starts (`GpuLevel.encode` makes them on demand).
  The layout benchmark also builds the search index once per graph and reports
  tab memory and the sequence worker with it.
- **Reason**: `bench/results.md` showed the 1M graph's GPU part at 748 MB
  against a 732 MB budget, with the tab at 1097 MB of 2048 MB. Level 0 kept the
  force buffer (8 B per point), the sorted and packed grid arrays (20 B per
  point) and the grid's cell tables after the layout was done. The positions,
  nodes, edges and heat buffers stay, because a refinement needs them and they
  cannot be rebuilt from the GPU alone.
- **Alternatives**: freeing the second positions buffer too (needs a copy of
  the latest positions first, for 8 B per point); dropping the edges and heat
  buffers (a refinement would need them uploaded again from memory the page no
  longer keeps); a tab target below 2 GB (not asked for).
- **Not measured**: the saving. The 200k and 1M graphs were not run in this
  session; the owner runs `npm run bench:layout` on another device and the
  table in `bench/results.md` carries the new numbers.

## 2026-11-15: Shipping (release stage 11.4)

- **Decision**: the site keeps a copy of itself in a hand-written service worker
  (`web/build/offline.ts` writes `sw.js` into the build; `src/offline.ts`
  registers it in production builds only). It caches every file of the build at
  install, answers same-origin reads from the cache and falls back to the
  network, and sends navigations to the cached page. The cache name carries a
  hash of the build, and a new worker waits until the old tabs close, so a
  running page never loses files it still has to load. Cross-origin requests,
  which include Open from URL, are not touched. The site deploys to GitHub
  Pages from the `Pages deploy` job of `.github/workflows/ci.yml` on every push to `main`. The
  accessibility audit is `tests/e2e/a11y.spec.ts` (every control has a name, ids
  are unique, the focus is outlined) plus the contrast tests of 11.2. The README
  carries one captioned GIF of a full walk through (about 1 MB, 1280 px wide), made
  from Playwright screenshots joined with ImageMagick, and the benchmark table.
- **Reason**: the spec asks for a site that works offline after the first load.
  The build is under 2 MB, so a full precache is simpler than a runtime cache
  and has no cold-start gap offline.
- **Alternatives**: Workbox (a dependency for a site of fixed files); `skipWaiting`
  (swaps the cache under a running page, whose lazily loaded workers could then
  miss a file); an axe dependency (rejected in 11.2); screenshots only in the
  README.
- **Not done here**: the 1M graph and the Bandage comparison, both owner-run
  measurements; Edge, Safari and a screen reader, listed in
  `docs/browser-checks.md`. The README benchmark table repeats the 2026-11-13
  numbers in `bench/results.md` until a new run replaces them.

## 2026-11-15: Screenshot baselines take CI's rendering

- **Decision**: the mitochondrion and chloroplast WebGL2 baselines are now the
  images CI's software rasteriser drew, and the baseline comparison allows 2% of
  pixels to differ instead of 1%. The comparison between WebGL2 and WebGPU keeps 1%.
- **Reason**: after the graph look change the first CI run differed from the
  baselines made on the owner's machine by 1.2% (mitochondrion) and 2.0%
  (chloroplast) of the pixels: smoothed thin curves anti-alias differently on
  another rasteriser. The same images differ from CI's by about 1.4% on this
  machine, so a 1% limit cannot hold on both.
- **Alternatives**: keeping 1% with CI's images (fails on the owner's machine);
  dropping the baselines (loses the regression check).

## 2026-11-16: One Pages deploy, after the gate

- **Decision**: `.github/workflows/pages.yml` is deleted. The site deploys only
  from the `Pages deploy` job of `ci.yml`, which needs the gate to pass.
- **Reason**: both workflows deployed on every push to `main`, racing for the
  same Pages environment, and `pages.yml` ran without waiting for the gate, so a

  `workflow_dispatch` to `ci.yml` for a manual redeploy (not wanted).

## 2026-11-16: Small gaps (milestone 13)

- **Selection summary**: several selected segments show N50 (the Overview's
  rule over the selected lengths), GC weighted by length over segments with a
  sequence, and the first 200 names with the true count; Copy names writes all
  of them in Bandage's export order. Chosen by the owner. The summary crosses
  the worker as five numbers (`SelectionSummary` gains `n50` and `gc`).
- **Stop**: Stop leaves the layout where it stands, marks it done and keeps
  pins; it is in the layout group and on the progress chip, on both backends.
  Chosen by the owner. The GPU `present` kernel shows any level through its
  ancestors, so a layout halted at a coarse level still draws every segment;
  dragging or refining needs level 0 and starts the refinement again.
  Alternative: discard the run (the graph would not draw until a restart).
- **Sheet focus**: below 900 px, Tab wraps inside the open sidebar or info
  sheet and Escape closes it. Focus goes back to the Show sidebar button (or the
  selected tab when the details close). A sheet open from the start does not
  take focus; one the user opens does. Alternative: make the rest of the page
  inert, which would hide the top bar from Tab until Escape.
- **The dots at the bottom left of the canvas**: they are data, not an overlay.
  With the acacia mitochondrion example open, a row of 11 dots sits at the
  bottom of the packed layout; the Overview counts 11 isolated segments, and
  each is a short segment drawn as a dot under the Detail threshold. Hovering
  one shows its name, length and depth, so nothing is added or removed. Seen
  in a 1440 px screenshot of all four examples with one segment selected.
- **No scale bar**: layout units are not bases, so a bar would show a false
  length. Chosen by the owner; no length is defined for layout units.
- **Baseline limit unchanged**: the spec's 2.0% against a 1% limit mixed two
  checks. The WebGL2 baseline comparison already allows 2% (2026-11-15, CI's
  rendering as the baseline); all four pass on this machine's real GPU, headed.
  The WebGL2 against WebGPU comparison keeps 1% and measures 0.000% on all four
  examples. No per-backend limit is needed.

## 2026-11-16: Measure and compare (milestone 14)

- **Machine**: every benchmark of this milestone runs on the AMD Ryzen 9 9950X
  desktop with an NVIDIA GeForce RTX 5060 (Blackwell), 32 threads and 31 GB,
  Windows 11 (10.0.26200), the machine of the 2026-11-13 layout numbers, so
  the README, the spec and `bench/results.md` stay on it. WSL 2 Ubuntu
  (kernel 6.6, 21 GB given to WSL) runs Bandage. Parts one to three run on it
  together, unattended, on an otherwise idle machine.
- **Toolchain on this machine**: a standalone Rust 1.92 in
  `C:\Program Files\Rust stable MSVC 1.92\bin` comes before rustup on PATH,
  so `rust-toolchain.toml` (1.99.1) was ignored and clippy failed. Every
  command here runs with `~/.cargo/bin` first on PATH; the system is unchanged.
- **Every benchmark**: `npm run bench:parse`, `npm run bench:layout` and
  `npm run bench:interaction` once each, then all of parts two and three.
  Chosen by the owner, so nothing is left to catch up.
- **A missed target does not stop the run**: parts two and three still run, and
  the miss is reported at the end with the per-level profile; nothing is cut or
  retuned before the owner sets the target. Chosen by the owner.
- **Every run is tried**: each tool runs five times on every graph, even after a
  run hit the 30 min cap. Chosen by the owner for the most complete numbers;
  this takes far longer than the 1 h 30 budget.
- **Open to a laid-out picture**: for GRAPE, from choosing the file to the
  layout reported done (settled); for Bandage and BandageNG, the wall time of
  `image` at the screenshot size, which loads, lays out and draws. Chosen by the
  owner, because Bandage only shows its finished layout.
- **PNG export at 200k**: GRAPE's `exportPng(1)` after the layout settled;
  BandageNG's `image` minus its `layout` (both medians); Bandage 0.9.0 has no
  layout-only command (its commands are load, info, image, querypaths and
  reduce), so its cell says so and the row compares the other two. Chosen by
  the owner over dropping the row.
- **Command lines checked**: `--help` of both tools, and the source:
  Bandage's `reduce` calls `saveVisibleGraphToGfa`
  ([command_line/reduce.cpp](https://github.com/rrwick/Bandage/blob/v0.9.0/command_line/reduce.cpp)),
  BandageNG's calls `gfa::saveVisibleGraph`
  ([command_line/reduce.cpp](https://github.com/asl/BandageNG/blob/v2026.11.1/command_line/reduce.cpp)),
  both after `--scope aroundnodes --nodes <list> --distance 0`. BandageNG's
  `layout` runs the same `GraphLayoutWorker` as its `image`
  ([command_line/layout.cpp](https://github.com/asl/BandageNG/blob/v2026.11.1/command_line/layout.cpp)).
  Both lay out with their defaults (Bandage `--iter 2`).
- **BandageNG cannot open the SPAdes sample**: v2026.11.1 aborts on
  `bacterial-spades.gfa` with "malformed path string for path
  'NODE_1_length_34015_cov_41.9818', cannot reconstruct path through the
  graph": SPAdes P lines step over scaffold gaps between segments with no
  link. The file is left as it is; its BandageNG cells say it did not open.

## 2026-11-16: Segment depths are doubles, as in Bandage

- **Decision**: `Segments.depth` holds an `f64` (Bandage keeps `double`); the
  WASM side narrows it to `f32` only for the GPU attribute
  (`segmentDepths`), and FASTA and GFA records cross the workers as a
  `Float64Array`.
- **Reason**: the Bandage comparison found GRAPE's whole-graph GFA of
  `mitochondrion-acacia-spades.gfa` one digit off on segment 30: the file's
  `dp:f:0.8158244860810399` became `0.81582451` as an `f32`, which `%g` rounds
  to `0.815825` where Bandage writes `0.815824`. Any depth whose seventh digit
  sits near a rounding boundary did the same, in GFA and FASTA headers.
- **Cost**: 4 B more per segment in the graph worker (0.8 MB at 200k, 4 MB at
  1M), inside its 300 B per segment budget.
- **Alternatives**: keeping the depth's text from the file (no help for KC,
  RC and FC depths, which are divided by the length); rounding the `f32` to
  six digits first (wrong whenever the `f32` crosses the boundary).

## 2026-11-16: What the milestone 14 run found and how it was measured

- **Click targets in the interaction benchmark**: on the 1M graph the 9th of
  20 clicks found no segment, because the first click opens the info panel
  and later targets, chosen before it opened, lay under it. The benchmark now
  opens the panel with one untimed click, then chooses targets, leaving out
  the segment that click selected. Measurements are unchanged in kind.
- **Runs the runner cannot trust are not recorded**: when Claude Code stopped
  the first run for low memory during Bandage's 1M run, every later process
  failed to start and 14 such runs were written as failures. They were removed
  from `bench/compare.json`, and the runner now stops instead of recording a
  run whose process did not start or was killed from outside.
- **Load while measuring**: League of Legends, Roblox and Discord were open on
  the machine through the run, at the owner's call ("just run it");
  `target/bench-logs/load.log` sampled CPU and memory every minute. CPU stayed
  at 2 to 18% between runs, with one 54% sample during the parse benchmark,
  whose numbers are far inside their targets.
- **Missed: 200k with the search index**: the tab reaches 1,453 MB against the
  1 GB target, because the sequence worker's index takes 1,080 MB. At 1M the
  index is past 1 GB and keeps only minimizers (957 MB), so the 1M tab stays
  at 1,619 of 2,048 MB. Not changed here; for the owner to decide.
- **Missed: 1M layout quality**: overlaps GPU 57,984 against CPU 10,744, as on
  2026-11-13; 11.3 did not change the layout. Not changed here.
- **GRAPE's exported PNG leaves the left third empty** at 1200 by 800: the
  export takes the whole canvas, while the fitted view leaves room for the
  sidebar (bench/screenshots/bandage/200000-grape.png). Bandage and BandageNG
  fill their images. Noted beside the picture table; for the owner to decide.
- **BandageNG timing falls back to a stopwatch**: one 200k layout run came back
  as -13,439,357,163 s, because Windows gave the process no exit time. The
  wrapper now also runs a stopwatch and uses it when the process's own times
  are not plausible; that run was removed and measured again (28.4 s).
- **The comparison adds 1M rows**: all three tools lay out the 1M graph within
  30 min, so the largest-graph row ties; open time and peak memory at 1M
  carry the difference instead. BandageNG's PNG export at 200k is shown as
  within noise, because its `image` and `layout` times overlap from run to run.
