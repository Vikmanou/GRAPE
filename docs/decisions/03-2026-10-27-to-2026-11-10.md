# Decisions, 2026-10-27 to 2026-11-10

## 2026-10-27: The examples ship gzipped from public/examples

- **Decision**: the four example graphs are stored gzipped (`gzip -9n`,
  470 KB in all) in `web/public/examples/` with a `CREDITS.md` that carries
  the CC-BY-4.0 attribution (Anna Syme 2020, Zenodo 5722622) and the MIT
  notices of odgi and minigraph, checked at their sources. The menu shows
  each credit and licence. Loading fetches the file from the site itself and
  opens it as any other file, so the parser's gzip path serves it.
- **Reason**: a fifth of the plain size; the menu is a same-origin request
  with no user data, within the privacy rules.
- **Alternatives**: plain files (2.6 MB); importing them into the bundle.

## 2026-10-27: Screenshot tests compare the backends and WebGL2 baselines

- **Decision**: `screenshots.spec.ts` draws each bundled example on WebGPU
  with `?layout=cpu` and on WebGL2 from the same seed, so both draw the
  same CPU layout, and fails when more than 1% of the canvas pixels differ by
  more than 48 summed over the channels (measured on this laptop: 0.000% on
  all four). That comparison needs WebGPU and runs under `check:headed`; CI
  checks the WebGL2 pictures against committed baselines
  (`screenshots.spec.ts-snapshots/*-webgl2-linux.png`, made with
  Playwright's headless Chromium and SwiftShader) with the same 1% tolerance.
- **Reason**: chosen by the owner; the GPU layout and the CPU layout differ,
  so only a shared layout compares renderers; CI has no WebGPU.
- **Alternatives**: only the headed comparison; baselines for both backends.

## 2026-10-27: Chain merging follows Bandage's "Merge all possible nodes"

- **Decision**: gfa-core `analysis/chains.rs` and `analysis/merge.rs` copy
  Bandage's `mergeAllPossible`, `mergeNodes` and `getUniqueNodeName`
  (graph/assemblygraph.cpp). Segments are visited in the order of
  Bandage's node map (name plus sign, byte order of UTF-8, which matches
  QString order outside the supplementary planes); each unvisited one grows
  forward, then backward, through links that are the only one at both ends.
  A merged segment's name joins its members' names with `_`, with `_2`,
  `_3`… while the name is taken; its depth is the members' depth weighted by
  their lengths; its sequence is the first member's followed by each next
  member's less the overlap of the link into it, untrimmed when the overlap
  is longer than the member (`modifySequenceUsingOverlap`, graph/path.cpp).
  Links from a chain back into itself are dropped, so a chain that is a whole
  circle loses its closing link, as in Bandage (chosen by the owner). Merged
  segments carry no custom colours or labels. Paths are mapped onto the
  merged segments, consecutive steps through one merged segment collapsing.
- **Where GRAPE differs**: an unknown depth is left out of the weighted mean
  instead of counting as Bandage's 1.0 (the same whenever every member has a
  depth or none does); segments with `*` sequences keep their `LN` lengths,
  where Bandage gives the merged node an empty sequence and length 0; GC is
  the members' GC weighted by the bases each keeps, an estimate.
- **Reason**: users moving from Bandage get the same merged graph; the
  property test (`tests/chains.rs`) checks that every walk through the
  merged graph spells the bases of the original walk it stands for.
- **Alternatives**: keeping a circle's closing link (recommended, declined
  by the owner); merging only for display, keeping the original segments.

## 2026-10-27: The GFA writer is Bandage's "Save entire graph to GFA"

- **Decision**: gfa-core `write/gfa.rs` writes what Bandage's
  `saveEntireGraphToGfa` writes (graph/assemblygraph.cpp,
  graph/debruijnnode.cpp, graph/debruijnedge.cpp, program/globals.cpp):
  `S` lines in the order of Bandage's node map (name plus `+`), each with
  its sequence or `*`, `LN:i`, the depth in the file's depth tag (`DP:f` as
  printf's `%g`, or `KC`/`RC`/`FC` as `int(depth × length + 0.5)`; the tag
  is the one the last segment with a depth used, KC for FASTG, none when no
  segment had one; an unknown depth counts as Bandage's 1.0), then
  `LB:z`, `L2:z`, `CL:z` and `C2:z` with Bandage's colour names
  (`getColourName`, first match in its list, else `#rrggbb`). Each link is
  written once as its positive edge (`isPositiveEdge`) with the overlap of
  the first line that gave it, `nM`, sorted by `compareEdgePointers`.
- **Where GRAPE differs**: a segment without a sequence keeps its real
  `LN` and counts from it, where Bandage measures the `*` and writes
  `LN:i:1` (chosen by the owner); edges Bandage's sort leaves tied are
  ordered by their names with signs; a link of unknown overlap is `0M`.
- **Reason**: exports match Bandage byte for byte for the same graph.
- **Alternatives**: writing `LN:i:1` as Bandage does; GRAPE's own order.

## 2026-10-28: Sequences can come from a separate FASTA file

- **Decision**: when a GFA file has no sequences (every `S` line `*`, as
  ABySS writes them), the Overview offers "Add sequences from FASTA…". The
  graph worker streams the FASTA file (plain or gzipped) through gfa-core's
  `FastaIndexer`, matching each record to a segment by the first word of its
  header; a matched segment takes the record's bases, length (replacing
  `LN`, reported) and GC, and components and stats are counted again. Plain
  FASTA is read back by offset from the file, gzipped FASTA is packed two
  bits per base as gzipped GFA is. New lengths lay the graph out again; new
  GC only recolours (`set-gc`). Raw `S` lines are no longer shown, since
  the sequences come from another file. Records that name no segment are
  counted, not kept.
- **Reason**: chosen by the owner for milestone 8's open question.
- **Alternatives**: no separate FASTA in v1 (recommended, declined by the
  owner); asking for the FASTA while the GFA loads.

## 2026-11-02: How sequence search finds and joins hits

- **Decision**: gfa-core `search/` holds a hash-bucket index of canonical
  15-mers over its own packed copy of the bases, seeds checked against those
  bases. Seeds cluster per segment and strand by diagonal; each cluster gets a
  Gotoh local alignment in a band reaching 64 bases past its seeds, with
  blastn's `-task blastn` scores (+2, -3, gap 5 + 2 per base;
  algo/blast/core/blast_options.h). A hit scores at least
  `min(40, 2 × query length)`. Cells carry their alignment's start and counts,
  so there is no traceback and memory stays one row wide. k-mers occurring
  over 4,096 times seed nothing and the UI says how many; each query keeps
  10,000 hits.
- **Reason**: spec's Features 7. Bandage's own `blastn` call runs BLAST's
  default task, megablast, which needs 28 exact bases; these scores suit a
  15-base seed. "Matches brute force" means: every strand's best alignment
  through an exact k-mer is reached, as seeding cannot promise alignments
  holding no seed.
- **Where hits can differ from a full alignment**: an indel longer than the
  band splits a hit in two.
- **Alternatives**: a traceback matrix (query × band bytes, 1 GB for a 10 Mb
  query); a suffix array (more memory, and it needs the bases contiguous).

## 2026-11-02: Past a 1 GB index, only minimizers are indexed

- **Decision**: every k-mer is indexed while buckets and entries fit 1 GB.
  Past that, robust winnowing (Schleimer et al. 2003) keeps a window's
  smallest hash, the window sized to fit; queries still look up all their
  k-mers. The panel states the exact match length that is always found,
  k + w - 1.
- **Reason**: chosen by the owner. WASM's 4 GB limit rules out a full index of
  multi-gigabase graphs.
- **Alternatives**: refusing such graphs; scanning all sequences per search.

## 2026-11-02: Hits join along links and bridge segments too short to seed

- **Decision**: two parts join when a link leads from one's strand to the
  other's and the query's gap is within 16 bases of what the walk spells, less
  the link's overlap. Otherwise a walk of up to 8 segments and 256 tries
  through segments that fit the gap may connect them, the walk aligning best
  to the query winning; so a gene reads as one hit through SNP bubbles.
- **Parts sharing query bases at the facing ends of a link join whatever its
  CIGAR says**: the Myxococcus sample writes `0M` on links whose segments share
  40 bases (`ks:i:41`), so the CIGAR cannot be trusted as a limit. The link
  must still exist.
- **Reason**: the spec joins adjacent hits only; bridging was chosen by the
  owner, as pangenome graphs have many segments under 15 bases
  (human-mito-4-haplotypes has a median of 1).
- **Alternatives**: joining direct links only; reading `ks` from the header,
  which only some tools write.

## 2026-11-02: Sequence search takes DNA only in v1

- **Decision**: queries hold A, C, G, T, U and IUPAC codes; other letters get
  a message. A U reads as T, and IUPAC codes count as mismatches.
- **Reason**: chosen by the owner for the spec's open question.
- **Alternatives**: protein queries through a six-frame translation and
  BLOSUM62, roughly tblastn.

## 2026-11-02: The known gene for sequence search is csgA in M. xanthus

- **Decision**: `testdata/csgA.fasta` (NCBI NC_008095.1:1520199-1520888, 690
  bases, public domain) must come back from the Myxococcus sample as one hit
  covering at least 99% at 100% identity. `tests/known_gene.rs` runs it on
  request (`--ignored`), as it needs the `--large` sample.
- **Reason**: chosen by the owner; a well studied gene whose hit crosses many
  short segments, so it proves joining too.
- **Alternatives**: 16S rRNA (multi-copy); a gene in the small SPAdes sample
  (none identified).

## 2026-11-02: Hits draw as bands placed along a ribbon by piece

- **Decision**: a hit's part is one instance per ribbon piece it crosses,
  drawn over everything else on both backends: the piece as drawn, cut flat
  where the hit starts or ends inside it and at the segment's own width, as
  Bandage draws hits (`Qt::FlatCap`, `m_width`, graph/graphicsitemnode.cpp).
  In double mode a hit shows on its own strand only; in single mode on the one
  ribbon, as Bandage does. A base's place goes by piece: `f × pieces` gives the
  piece and the fraction along it. A band stays at least 1.5 pixels long
  however far out the view is.
- **Where GRAPE differs**: Bandage measures a hit's fraction by arc length
  along the node (`findLocationOnPath`). Pieces share a rest length, so the two
  agree once a layout settles, and piece positions need no work as points move
  during a layout or a drag.
- **Reason**: bands read live positions in the shader, so a running layout
  keeps them in place. On WebGPU the instances bind to `visible_pieces`, which
  keeps the vertex stage within the default of 8 storage buffers.
- **Alternatives**: a per-segment attribute holding a fraction range (one
  range per segment, and hits can overlap); per-piece colours rebuilt on each
  search.

## 2026-11-09: Share links: format 1 and what it carries

- **Decision**: a share link is the page's address with the fragment
  `#v=1.<payload>`, the payload JSON compressed with `deflate-raw` and
  written in base64url (spec, Features 12). The `1` is the format version;
  a link of another version is refused with a message. It carries the file's
  fingerprint (size, segment count, SHA-256 of the first MiB), the layout's
  seed and quality and which layout made it (`gpu` on WebGPU, `cpu` for the
  layout worker's), chain merging on or off, the camera (centre in layout
  units, CSS pixels per unit), the display options with the colour range,
  the label settings, the size and depth filters, the selected segments'
  names and the highlighted paths' names. Owner's choices: search queries are
  never in it, as a query is a sequence and links carry none (the spec's
  Features text listed them; the privacy rule wins); the neighbourhood and
  component filters stay out; the address of a file opened from a URL goes in
  only when the sharer ticks a box, off by default, because addresses can
  hold access keys, and the recipient downloads it only by clicking. A link
  past 8,000 characters drops the selection and says so. Query parameters
  such as `?renderer=webgl2` are not part of the link (decision of
  2026-10-27).
- **Restoring**: the link waits until a file is opened, checks the
  fingerprint, and on a match lays the graph out from the link's seed, then
  merges, filters, highlights and colours as the link says, and sets the
  camera and the selection once the layout settles. A different file opens as
  it is with a message. Opened on the other kind of layout (WebGPU against
  WebGL2), the same seed gives other positions, so the camera starts fitted
  and a message points to session files. The fragment is cleared once used,
  and read again on `hashchange`, since a link pasted into a tab already on
  GRAPE does not reload the page.
- **Reason**: the owner's answers to the plan's questions; the fragment never
  reaches a server.
- **Alternatives**: queries in the link, opt-in or always; every filter as
  seed names and step counts; the spec's field list only.

## 2026-11-09: Session files keep float32 positions and are read in the graph worker

- **Decision**: a session file (`.grape.json.gz`) is gzipped JSON:
  `{"grape":"session","version":1,"view":<a share link's state>,"positions":{"encoding":"float32le-base64","points":n,"data":"..."}}`.
  Positions are float32, not the spec's float16 (owner's choice): float16
  steps by a whole unit past 2,048 and by 32 past 32,768, against ribbons 5
  units wide. The graph worker writes and reads it, as a large graph's
  positions make a JSON string too long for the main thread. Opening one
  waits for its graph like a link; the layout worker then builds the geometry
  and a grid around the saved positions (gfa-core `layout::Fixed`) and no
  layout runs. A session never holds the file's address. Pins are not
  saved; dragging and re-layout of the selection need a restarted layout.
- **Reason**: positions identical bit for bit reproduce the view exactly on
  either backend, which a seed cannot across GPUs.
- **Alternatives**: float16 as the spec said; float32 anchors with float16
  steps along each chain; a binary container.

## 2026-11-09: PNG and SVG show the canvas as drawn

- **Decision**: a PNG is the whole canvas, panels' area included, drawn
  offscreen `scale` times larger (1, 2 or 4, less if the image would pass
  16,384 pixels a side or 2^26 pixels) in tiles of at most 2,048 pixels,
  each read back and composed on an `OffscreenCanvas`. A view field,
  `pixelScale`, scales everything set in pixels (minimum widths, outlines,
  link fade, dots, label size and halo) so the image is the screen's picture
  at higher resolution. Tiles sit at whole pixels of the image, so labels
  round alike in every tile. An SVG is built on the main thread in slices of
  2,000 segments between yields, from the same shapes the shaders draw
  (`export/shapes.ts` mirrors `graph.wgsl`): links under ribbons, the
  selection outlined on top, dimming, dots, bands and labels. Past 50,000
  segments in view it refuses with a message rather than writing part of the
  view. Double mode's arrowheads are not drawn in SVG.
- **Reason**: small tiles keep each readback and `putImageData` within a
  frame; Bandage's image export renders its scene through Qt and cannot be
  matched byte for byte, so the picture follows the screen instead.
- **Alternatives**: tiles at the GPU's texture limit; a worker for the SVG;
  writing the first 50,000 segments.

## 2026-11-09: GFA of a selection or of what is shown is Bandage's visible-graph save

- **Decision**: the GFA writer takes an optional bitset of segments to keep
  and then writes what Bandage's `saveVisibleGraphToGfa`
  (graph/assemblygraph.cpp) writes: the kept segments in node-map order and
  the links whose two ends are both kept, sorted by `compareEdgePointers`.
  "What is shown" is the filters' visible set, read from the engine. FASTA
  of what is shown uses the selected-sequences writer on that set.
- **Reason**: exports match Bandage (decision of 2026-10-26).
- **Alternatives**: links with only one kept end.

## 2026-11-09: Open from URL fetches without credentials

- **Decision**: the browser fetches the address the user types with
  `credentials: 'omit'` and `referrerPolicy: 'no-referrer'`, reports progress
  when the server gives a length, and can be cancelled from the status bar.
  A fetch that never starts says the server may be unreachable or refuse
  other sites (CORS), as the browser does not say which. The download is
  held as a `File` on the main thread before parsing, as a dropped file is.
- **Reason**: the only request involving user data stays user-initiated and
  sends nothing but the address.
- **Alternatives**: fetching in the graph worker; streaming straight into
  the parser.

## 2026-11-09: Graphs in share links are packed by a context-mixing codec in gfa-core

- **Decision**: `gfa_core::pack` codes the file losslessly. It splits each
  line into text, sequence lengths, 2-bit bases and a side stream for case
  and non-ACGT runs, and codes each stream with a binary arithmetic coder
  and logistic mixing after lpaq1. Bases mix order 1 to 24 contexts, with
  GeCo's inverted repeats from order 11 up, plus forward and
  reverse-complement match models. The text model adds contexts from the
  same column of the previous line of the same record type. Everything is
  integer arithmetic, so native and WASM code the same bits. A CRC-32 of the
  file catches a cut or altered link.
- **Reason**: a pasted link must hold the whole graph. Brotli is not in
  every browser's `CompressionStream` and zstd is in none, and both stop
  near 2 bits per base. Measured against xz -9e on the samples, packed size
  is 26% smaller on SARS-CoV-2 (9,545 against 12,900 bytes), 16% on LPA
  (68,603 against 82,500), 9% on the Acacia mitochondrion (202,026 against
  222,380) and 2.5% on MHC (1,121,259 against 1,149,748). Bases cost 1.67
  bits on MHC and 1.89 on the plant mitochondrion, close to what
  reference-free DNA compressors reach, and changing the mixer rate or the
  counter limits moved the size by under 0.4%. Native speed is about 1 MB
  of file a second each way.
- **Alternatives**: deflate-raw through `CompressionStream`; a zstd or xz
  build in WASM; dropping tags and comments for a smaller lossy link.

## 2026-11-10: A share link can carry the whole graph

- **Decision**: besides the view-only link, the share menu makes a link with
  the graph: `#g=1.` then base64url of parts in a row (kind, name, data;
  web/src/workers/pack/payload.ts), the view's JSON and the graph file (and
  any attached FASTA) each packed by `gfa_core::pack`. Gzip is undone first,
  so the recipient gets the file as the parser saw it, named without `.gz`.
  The link has no positions: the recipient lays it out from the seed. Its
  fingerprint is not checked, since the CRC already proves the bytes. Packing
  stops once the link would pass 2 MiB, Chrome's `kMaxURLChars`
  (url/url_constants.h); the menu then says the graph is too large. Packing
  and unpacking run in a worker started for the one request, so the graph
  worker keeps answering and Cancel terminates it. Open URL accepts a pasted
  link, found by text, since Firefox's URL parser and `type="url"` check
  refuse links over 1 MiB.
- **Reason**: the owner asked that a pasted link open the sharer's graph
  with no upload and nothing else to open. Without a server, the graph can
  only travel in the link. Measured URL limits: Chromium 156 opens 2,097,000
  characters and refuses 2,200,000; Firefox 157 opens 1,048,570 and refuses
  1,048,575. WebKit could not run on this machine (Playwright's build needs
  Ubuntu libraries), so Safari's limit is not measured. Pack and unpack in
  Chromium: 9.2 and 9.3 s for the MHC sample (1,495,569 characters), 1.4 and
  1.6 s for the Acacia mitochondrion (269,933).
- **Alternatives**: a server or peer-to-peer transfer (against the privacy
  rules); a 1 MiB cap so every link opens from Firefox's address bar; base
  32768 Unicode text, 2.5 times fewer characters but 3 times more bytes, and
  mangled by some apps; positions in the link.

## 2026-11-10: Share links always carry the graph; no view-only links

- **Decision**: the view-only link (`#v=1`, a fingerprint and the view) is
  removed, with its option to include the file's address and the notice
  that waited for the file. The share menu makes only the link with the
  graph (`#g=1`). An old `#v=` link says it holds no graph. Session files
  stay, but open only onto the graph already loaded: with no graph or
  another one, a notice says so instead of waiting.
- **Reason**: the owner found a link that needs its file sent separately
  useless, and the waiting notice confusing.
- **Alternatives**: keeping view-only links for graphs too large to pack;
  sessions that wait for their graph without a notice.
