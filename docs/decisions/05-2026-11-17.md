# Decisions, 2026-11-17

## 2026-11-17: Installable app (milestone 15), the owner's answers

- **Name**: `GPU-Rendered Assembly Path Explorer`; short name `GRAPE` (owner).
- **Icon**: the owner's `GRAPE_Icon.png` (1254 by 1254, transparent), and a
  banner `GRAPE_Banner.png` (2172 by 724) for the README. The owner put both in
  `web/public`, but everything there goes into the offline copy and the two
  files weigh 1.7 MB: the icon moves to `web/assets-src/`, where the spec keeps
  the source, and the banner to `assets/grape-banner.png` beside the README's
  other pictures, replacing `assets/grape-logo.png`. The icons the site serves are rendered from them by
  `scripts/app-icons.mjs` and never redrawn.
- **Tab and iOS icon**: both use the new icon, and so does the top bar beside
  the name (owner: "update across the website to use the icon"). `favicon.svg`
  is removed.
- **Description**: the page's meta description, reused (owner).
- **Colours** (left to Claude by the owner, "anything that fits"): the app's own
  palette, so the installed window's title bar matches the top bar and the
  splash matches the canvas. Theme colour `#ebe6da` light and `#1c2128` dark
  (the `--chrome` token); background `#f6f2e9` (the light `--bg`; a manifest has
  one background colour, and the light theme is the default); behind the
  maskable icon `#f6f2e9`, where the purple art keeps its contrast.
- **Maskable icon**: the art reaches the corners (the leaf), outside the
  central 80% circle that a maskable crop keeps, so the maskable icon is the
  same art scaled down until its farthest opaque pixel lies inside that circle,
  on the backdrop colour. Scaled, not redrawn.
- **File handler** (left to Claude, "do what's best"): yes, for `.gfa`,
  `.gfa.gz` and `.fastg`, each under its own MIME type (`text/x-gfa`,
  `application/x-gfa-gzip`, `text/x-fastg`). The file still never leaves the
  browser: `launchQueue` hands the page a local file handle. Chromium only.
- **Which names match was tested, not assumed** (owner, 2026-11-17): the built
  app was installed in Edge through the DevTools `PWA` domain and
  `PWA.launchFilesInApp` was asked for each name. Chromium compares
  `FilePath::Extension()`, which reads a two-part extension when the last part
  is `gz` (or another compression suffix) and the part before it has 1 to 4
  characters
  ([file_path.cc](https://source.chromium.org/chromium/chromium/src/+/main:base/files/file_path.cc)),
  on every platform. So `a.gfa.gz`, `a.v2.gfa.gz` and `A.GFA.GZ` match `.gfa.gz`;
  `a.fastg.gz` has the extension `.gz` and can never match a `.fastg.gz`
  entry. A bare `.gz` was tested too: it adds `.fastg.gz`, but also `.fastq.gz`
  reads and any `name.gz`, offering GRAPE for files it cannot open, and adds
  nothing for `.gfa.gz`. So `.fastg.gz` opens from inside the app only.
- **Own MIME types, for Linux**: on Linux Chromium writes the accept MIME types
  into the app's `.desktop` file and registers each extension as a glob under
  that type with `xdg-mime`
  ([shell_integration_linux.cc](https://source.chromium.org/chromium/chromium/src/+/main:chrome/browser/shell_integration_linux.cc)).
  The first manifest used `application/octet-stream`, which would have listed
  GRAPE for every unrecognised binary file on a Linux desktop. Windows keys on
  extensions only. Shared MIME-info prefers the longest glob, so `*.gfa.gz`
  wins over `*.gz` there.
- **`.layout` is not handled**: opening a layout applies it to the graph already
  open, so launching the app on one alone does nothing, and a `*.layout` glob
  could retype other programs' files on Linux. It opens from the Open menu.
- **Not tested here**: whether the desktop lists GRAPE under Open with. The
  automated install wrote no association at all on Windows, not even for
  `.gfa`, and the launched file opened no window (the first launch asks the
  user to allow the file types). Windows writes `.gfa.gz` as written
  (`HKCU\Software\Classes\.gfa.gz\OpenWithProgids`) and Explorer may key on
  `.gz` only; Linux has no such limit. Both stay hand checks in
  `docs/browser-checks.md`.
- **Screenshots** (left to Claude): yes, one wide (1280 by 720) and one narrow
  (390 by 844), taken fresh of an example graph, so Chrome shows the larger
  install dialog.
- **Alternatives**: no file handler (the owner did not mind, and the handler
  costs a few lines); `.gfa` only (the picker's list is what users already
  get); reusing `bench/screenshots` (those are benchmark views at 1200 by 800,
  not the sizes the install dialog wants).
- **Installability is checked through Chromium's parsed manifest too**:
  `Page.getInstallabilityErrors` returns no error even for a page with no
  manifest in the Chromium that Playwright 1.64 runs (Chrome relaxed its install criteria), so
  `tests/e2e/install.spec.ts` also reads `Page.getAppManifest` and expects the
  manifest found, parsed without errors, standalone, with three icons and two
  screenshots. CDP leaves `short_name` and `file_handlers` out of its parsed
  copy; the spec checks those in the JSON, and the file handler is a hand check
  in `docs/browser-checks.md`.
- **The production-build specs run Vite with node**: `offline.spec.ts` called
  `npx` without a shell, which fails on Windows (ENOENT), one of the seven
  Windows failures noted in milestone 14. The shared `tests/e2e/serveBuild.ts`
  runs Vite's own script with the running node instead, which needs no shell.
- **Checked by Claude, not left to the hand list** (2026-11-17, owner: "find a way"):
  - Android, on the Android Studio emulator (Pixel, API 34, Chrome 113, whose
    install criteria are still the strict ones): no installability errors;
    the menu offers Install app; the install sheet shows the icon, the
    description and the narrow screenshot; the home screen icon is whole;
    launched from it, the app runs standalone (`display-mode: standalone`,
    no address bar, the cream theme colour in the status bar); with Wi-Fi and
    data off, the server unreachable and Chrome stopped, it starts from the
    icon and opens an example. From `localhost` Chrome makes a shortcut, not a
    WebAPK, so the full-bleed maskable icon itself shows only from the live
    https site.
  - Edge on Windows, installed through the DevTools `PWA` domain: a cold
    start with no server and the browser offline opens an example; a new
    build (another cache name) is in use from the first launch after the
    app's windows close, as for a tab; the window is standalone once the
    user display mode is standalone (a DevTools install defaults it to a
    browser tab, a click on Install does not).
  - Icons, by pixels: the maskable and iOS icons have no transparent pixel,
    the cream backdrop, and all art inside the central 80% circle. The first
    render missed by 0.3 px of softened edge; `scripts/app-icons.mjs` now
    keeps 2 px to spare.
  - The page's side of a file launch: `tests/e2e/launch-file.spec.ts` hands
    the app a real file handle through a stand-in `launchQueue`, and the file
    opens. Chromium's own `launchQueue` is a read-only property of window.
- **Still by hand**: Safari (no Mac here); and the desktop's Open with list
  and the browser's "open these file types?" prompt, which need a person to
  click Install and allow; Claude Code declined to drive those dialogs with
  UI Automation.

## 2026-11-17: Browser and assistive checks (milestone 16), how they run

- **Owner's answers**: the owner has an iPhone or iPad but no Mac, so Safari
  on macOS (26 and 15 to 18) is a recorded gap and iOS Safari is checked by
  the owner from a short list. Claude installs NVDA and reads what it spoke
  from its log instead of the owner listening. Playwright's WebKit on Windows
  stands in for Safari's engine, recorded as WebKit and never as Safari.
- **The spec's "WebKit does not run on Fedora"** no longer applies: the build
  machine is Windows 11, where Playwright's WebKit runs.
- **200% zoom is a spec, not a hand check**: `tests/e2e/zoom.spec.ts` lays the
  page out at half of a 1280 by 800 and a 1920 by 1080 window with two device
  pixels per CSS pixel, which is what 200% browser zoom does, and checks that
  every control in the sidebar tabs, the menus and the info panel can be
  scrolled to by a person and is the element under its own centre. A script
  can scroll an `overflow: hidden` box that a person cannot, so a control that
  only a script could reach fails too. The 390 px window stays with
  `narrow.spec.ts`.
- **Found by it**: at 200% of 1920 by 1080 (960 by 540) the Export menu ran
  past the bottom of the window and its last items could not be reached. The
  desktop menu popup is now capped at the window height less the top bar and
  scrolls, as the narrow layout's already did.
- **Screen reader, NVDA 2026.3.1 with Edge 157**: Claude ran a portable NVDA
  from the scratchpad with the silent synth and read its I/O log. NVDA
  follows whatever window has system focus, so it runs only while the owner
  is away from the PC; the first try caught the owner's other windows, and
  that log was deleted at once. The tabs were heard as "Overview, tab,
  selected, 1 of 4" and so on, but two gaps were found and fixed:
  - Home and End did nothing on the tab list. They now move to the first and
    last tab, as the WAI-ARIA tabs pattern describes.
  - A selection was silent: the info panel appears with no announcement, and
    a live region mounted together with its text is often not read. An
    always-mounted polite region in the info panel now says "Segment 53
    selected" or "2 segments selected" however the selection was made. With
    Find, NVDA reads Find's own "Selected 1 segment." first, then the name;
    the repetition was kept because the second line carries the name.
- **WebKit on Windows draws WebGL2 wrongly**: in Playwright's WebKit 27.2 on
  Windows the WebGL2 picture is wrong (straight segments, far-flung links,
  clicks select nothing), while Chromium on WebGL2 is right. The layout
  positions hash the same in both, a standalone page shows WebKit uploads
  and samples the same RG32F and RG32UI textures correctly, the canvas size
  matches, and every program's uniform offsets match. The owner opened the
  live site on an iPad with `?renderer=webgl2` and Safari draws it
  correctly, so this is recorded as a bug of WebKit's Windows port and GRAPE
  is not changed for it.

- **The rest is left unchecked by the owner's choice**: the owner chose not
  to run the remaining by-hand lines (Safari on iPadOS beyond the WebGL2
  picture, the desktop install dialog, the Android icon mask, the Safari
  home-screen icon, and Open with on Windows). They stay unticked in
  `docs/browser-checks.md`, marked as not checked by decision, so a later
  release can pick them up. Safari's share-link size limit stays unmeasured.
